# Prompt 优化器 Skill 指南 (RSCIT + CoT)

本 Skill 旨在为后续的开发提问提供一个系统化的 prompt 优化框架。通过将模糊、碎片化的开发需求转化为结构明确、约束严谨的 RSCIT 提示词，并要求 AI 采用 CoT (Chain of Thought) 思维链进行推导，从而最大化地提升代码生成 and 问题解决的质量。

## 1. RSCIT 提示词架构

任何开发提问在提交给 AI 之前，都应当被重构为以下五个核心维度：

*   **R - Role (角色设定)**
    *   **定义**：指明 AI 的专家身份与技能边界。
    *   **示例**：`你是一位精通 React 18 和 Vite 构建优化的前端架构师...`
*   **S - Scenario (场景上下文)**
    *   **定义**：交代项目的技术栈、现有代码结构、运行环境、系统约束或当前的 Bug 现象。
    *   **示例**：`项目采用 Express + Prisma ORM + MySQL 8.0。目前在执行大批量数据插入时，内存占用过高，出现了 OOM 崩溃...`
*   **C - Constraint (约束条件)**
    *   **定义**：绝对禁止的做法、必须遵守的规范、硬性性能指标、安全规范。
    *   **示例**：`不要修改现有的 Prisma Schema；禁止引入第三方大型依赖；代码中必须包含异常捕获与日志记录...`
*   **I - Instruction (执行指令)**
    *   **定义**：指导 AI 执行的具体步骤，通常是按逻辑顺序排列 of actions。
    *   **示例**：`1. 剖析内存泄露原因；2. 设计分批写入算法；3. 提供重构后的服务层代码；4. 编写对应的单元测试。`
*   **T - Target (交付目标)**
    *   **定义**：规定输出的格式、结构和展示方式。
    *   **示例**：`请以 Diff 块的格式提供代码修改方案，并以表格形式对比优化前后的内存预期消耗。`

## 2. CoT (思维链) 推导机制

在 Prompt 中显式开启 CoT 推导，能够促使大模型进行深度推理而非仅凭概率输出代码。

*   **激活句式**：在 Prompt 的 Instruction 或 Constraint 中注入以下引导语：
    *   `在给出任何代码或结论之前，请务必在 <thought> 标签内进行深度的思维链推导：分析当前问题的根源、权衡至少两种备选方案的优劣、评估方案对现有系统的潜在负面影响，然后再输出最终方案。`
*   **思维链要点**：
    1.  **现状剖析**：理解输入数据的结构和当前逻辑缺陷。
    2.  **多方案对比**：方案 A vs 方案 B 的时间/空间复杂度与实现难度对比。
    3.  **副作用评估**：该改动是否会破坏现有的 API 兼容性或触发数据库锁冲突？

## 3. Prompt 优化工作流与模板

当需要优化一个开发提问时，请调用以下结构化模板：

### 提示词优化模板
```markdown
# 优化后的 Prompt 架构

## [Role] 角色
你是一个精通 [领域/技术栈] 的资深开发专家。你拥有极强的 [特长]，习惯编写类型安全、高内聚低耦合且易于测试的代码。

## [Scenario] 开发背景
- **项目技术栈**：[例如：Vite + React 18 + Zustand + TailwindCSS]
- **当前现状**：[当前运行的代码片段、配置文件、或需求背景描述]
- **遇到的问题**：[报错信息、性能瓶颈或期望新增的功能]

## [Constraint] 关键约束
1. **安全与规范**：[例如：禁止直接暴露敏感凭证，使用 HttpOnly Cookies]
2. **兼容性**：[例如：必须兼容现有的 API 路由，保留原有的注释]
3. **实现限制**：[例如：不引入额外的 npm 包，首选原生或项目中已有的库]
4. **思考过程**：在输出任何代码前，必须先在 `<thought>` 中写明你的推理路径。

## [Instruction] 执行步骤
1. **分析**：[分析步骤描述]
2. **设计**：[方案设计与选型]
3. **实现**：[具体的编码实现指导]
4. **验证**：[验证与测试思路]

## [Target] 交付格式
- [例如：提供修改前后的代码 Diff / 提供完整的模块文件]
- [例如：对核心改动点提供简明的技术 rationale 解释]
```

## 4. 优化示例

### ❌ 原始提问 (模糊且碎片化)
> "帮我用 Express 写一个数据导出的接口，要能支持 CSV 格式，另外不要让用户频繁导出。"

### ⚙️ 优化后的提问 (遵循 RSCIT + CoT)
```markdown
# 角色
你是一个精通 Node.js 安全架构的后端资深工程师。

# 背景
- **技术栈**：Express 4.21 + Prisma ORM + MySQL 8.0。
- **现状**：需要新增一个导出训练记录的 API：`/api/v1/export?format=csv`。数据源自 `WorkoutRecord` 和 `ExerciseSet` 两张表。
- **关联文件**：[server/src/modules/export/export.routes.js](file:///d:/PersonalProjects/FitLog/server/src/modules/export/export.routes.js)

# 关键约束
1. **防滥用限制**：每个用户（通过 JWT 认证获取的 `userId`）每天限制最多导出 3 次。
2. **零副作用**：不能修改现有的 MySQL Schema；不能引入除 `csv-writer` 或原生拼接之外的重型依赖。
3. **思维链推导**：请在输出代码前，于 `<thought>` 块中详细推导：
   - 如何在不引入 Redis 的情况下，利用内存缓存或数据库查询轻量级地实现“每日限制 3 次”？
   - 评估大批量数据下，同步生成 CSV 对 Node.js 事件循环的阻塞风险并给出应对策略。

# 执行步骤
1. 设计每日导出限流逻辑。
2. 编写 Service 层代码：从数据库中拉取当前用户的训练数据，并将多对多的数据结构扁平化为符合 CSV 每行一个 Set 的格式。
3. 编写 Controller 层，配置合适的 HTTP 响应头以实现浏览器静默下载。

# 交付格式
- 以统一的代码块给出 `export.controller.js` 的完整实现。
- 提供核心限流逻辑 of the change.
```
